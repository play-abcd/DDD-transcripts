## Before writing a new issue

1. **Search first, including `issues/completed/`.** Grep the issue tree for
   the feature's nouns, not just the likely title. A completed issue about the
   same machinery is reopened and extended rather than duplicated: history is
   more useful stacked vertically in one file than spread across several.
2. **Pick the phase by what the work builds on**, not by when it is being
   done. Lower numbers are foundations; later issues depend on earlier ones.
3. **Take the number from the tool:** `validate-issues <project> --next
   <phase>`.
   It reads the project's own naming shape (522, 1001, 9-007, A04) and never
   reuses a number that a completed file already holds.
4. **Write the blueprint** with the three sections CLAUDE.md requires, plus
   link fields in the shape the project already uses (look at a neighbour).
   Name related functions, structures and files instead of pasting code.
5. **Check it:** `validate-issues <project> --file <new-issue>`, and fix what it
   reports on the new file. If the new issue blocks or is blocked by others,
   add the matching line to the other side too.

## While working

- Keep **Current Behavior** true. It is the only section that changes while
  an issue is in progress; rewrite it in place rather than appending a log.
- A question that surfaces is written into the issue (an "Open questions"
  section) and then asked. An issue with an unanswered question is in
  progress, not done.
- Anything discovered that changes another issue's assumptions is written into
  that issue now, not at completion.

## Splitting into sub-issues

Split when an issue holds work streams that could be built, tested or reviewed
separately, or when it cannot be finished in one sitting. Do not split an issue
that is already one mechanism. When splitting, produce and then write out:

1. **A table** — `| ID | Name | Dependencies | Description |`, where ID is the
   parent number plus a lower-case letter (103a, 103b), Name is dash-separated
   lower-case words, Dependencies is "None" or sibling IDs.
2. **The rationale** — the distinct work streams, why one issue cannot hold
   them, what splitting buys.
3. **The execution order** — a small dependency graph, e.g.
   `103a (foundation) → 103b (needs 103a) → 103c (parallel with 103b)`.

Each row becomes a file `{parent}{letter}-{name}.md` with the three sections.
The parent keeps its blueprint and gains a short list of its sub-issues; the
analysis itself is not appended to the parent (that would be worklog, not
blueprint). Run `validate-issues` afterwards: it reports orphaned sub-issues
and one-sided links.

## Completing an issue

An issue is complete only when nothing in it is deferred and no open question
is unanswered. Then, in this order:

1. **Run the project's tests.** A fixed bug gets a test that would have caught
   it.
2. **Rewrite the issue as the blueprint of what was built**: Current Behavior
   states the built system; steps name the real functions and files; decisions
   not taken are stated with their reason. Poetry the owner wrote during the
   work goes into the issue verbatim.
3. **Move it** into `issues/completed/` (`git mv`, so the history follows).
4. **Update `issues/phase-<N>-progress.md`** for that phase. Take counts from
   `progress-dashboard.lua <project> -m`, or better, name the command instead
   of copying numbers that will go stale.
5. **Update related issues** whose Current Behavior or assumptions changed.
6. **Run `validate-issues <project>`** and fix new findings that the change
   caused. Findings older than the change are reported to the owner, not
   silently fixed in passing.
7. **Commit** as below.

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and every
changed transcript of the commit's projects rides along — the session's own
project folder and the projects of the files it commits — this
conversation's and any other's left behind (a session that committed, talked
on and quit), so each project's story in git stays whole.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) plus those transcripts, and
   never touches the shared staging area, so nothing another
   session has staged can ride along. Plain `git commit` is refused by the
   commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**
  (a script you ran, a generator, `sed`, a rename): record them with
  `claim-own-change <file>` and say so in the commit message.
- **Nothing to commit, but the work is there**: an earlier session wrote it
  and ended, or the machine rebooted and emptied the ledgers. Look first with
  `adopt-left-behind-changes <repo> --dry-run -- <path>...`, then adopt and
  commit one batch at a time with `commit-own-changes <repo> -F - --
  <path>...`. Lines reported as **held** belong to another session. Take them
  (`--from <session>`) only if that session has finished, and ask the owner
  if unsure. Say in the commit message that the work was adopted and from
  whom. This is the route for a left-behind backlog, not the token.
- **A warning about the shared staging area** means someone had staged that
  file by hand in a way that overlaps your commit; their entry was left alone.
  Tell the owner.

The one-time permission tokens (`/tmp/claude-allow-*`) belong to the person.
Never create one; if a gate names a token, relay the gate's message and let
the owner decide.

## Your email: DKIM

Your Squarespace mailbox is run by a company called **Titan**. Good news: a
program can send through it. The server is `smtp.titan.email`, port 465, and it
logs in with the mailbox's address and password. So the claim page could send as

**What DKIM is.** Think of a wax seal on a letter.

1. Titan keeps a secret key. Every email it sends for you gets a signature: a
   long number worked out from the message and that secret key.
2. The matching *public* key gets published in your domain's DNS. DNS is the
   public phone book that says what `abcd-games.net` means.
3. When Gmail receives your email, it looks up that public key and checks the
   signature. If it matches, the email really came from a server holding your
   key, and nobody changed it on the way.

Right now there's no public key in the phone book, so there's nothing to check.
Mail with no seal is the first kind spam filters distrust. That's your
"untrusted".

It has two partners. **SPF** is a line in DNS listing which servers may send for
your domain. **DMARC** tells receivers what to do when a check fails.

**How to fix it** (it's a few clicks, from Titan's own guide):

1. Log in to the Titan control panel and open the **"Email Reputation"** tab.
2. Under **"Add DKIM record"**, click **Add**. It shows you a name and a long
   value.
3. In Squarespace, go to your domain, then **DNS Settings**, and add that
   record. Squarespace may hand it over as a CNAME record.
4. Wait a little while for it to spread, then check Titan's tab for a green
   tick.

# Transcript care

The transcripts are the record of how each project was made, and for most of
them the session log they were exported from is gone. A transcript whose log is
gone cannot be rebuilt by anything, so every tool here either reads, or
snapshots before it writes.

Every tool below lives in `/home/ritz/programming/ai-stuff/scripts/` (called
`SCRIPTS` here) unless named otherwise. Call them by absolute path; they are
the one home, and this skill does not carry copies.

## Two rules the whole system rests on

- **The header is the identity.** A transcript's first line is
  `# Conversation Summary: <conversation id>`. That line, never the filename,
  says which conversation a file holds. `SCRIPTS/libs/transcript-discovery.sh`
  is the rulebook for recognising and naming transcripts; any new tool sources
  it rather than re-deciding.
- **The exporter is the only namer.** Only `SCRIPTS/backup-conversations`, run
  by the Stop hook after every reply, names, renames or removes a transcript.
  It turns each session log into markdown through
  `SCRIPTS/libs/conversation-parser.lua`. A rename by hand or by another tool
  is overwritten on the next reply. If a name is wrong, fix the exporter.

The history of why is in `SCRIPTS/issues/transcript-system-progress.md`.

## Maintenance, in this order

Run these in order whenever the exporter or parser changed, or the archive
looks wrong. Each step's output decides whether the next is safe.

1. **Snapshot.** `SCRIPTS/backup-transcript-corpus` copies every transcript on
   the machine with its modification time kept (often the only evidence of
   when a conversation happened), plus the prompt history, then re-reads the
   copy to verify it and writes a restore script. Nothing is rewritten until
   this has passed.
2. **Report the rebuild.** `SCRIPTS/rederive-transcripts` (no flags) lists which
   transcripts still have their session log and would be rebuilt, and which
   are frozen. It writes nothing. `--only <path>` narrows it to one project.
3. **Rebuild.** `SCRIPTS/rederive-transcripts --write`, only after reading step
   2's report with the person.
4. **Filing check.** `SCRIPTS/check-transcripts-are-filed-right` exits 1 if any
   transcript sits in a different project from its conversation record. It
   reports; it never moves files (see the naming rule).
5. **Tests.** Run every test in `SCRIPTS/tests/`: the `.lua` files with
   `luajit`, the `.sh` files with `bash`. They cover the parser's handling of
   time zones, quoted lines, harness traffic, narration and models, and the
   exporter's guards.

If any step fails, stop there and report it. A partially rebuilt archive with
a failing filing check is worse than the archive before step 3.

## Editing a transcript: patches, never hand edits

A hand edit is overwritten by the next export. To change what a transcript
says, write a patch; the exporter re-applies it on every export
(`SCRIPTS/transcript-patches`, design in
`SCRIPTS/issues/036-transcript-patches.md`).

- **Add one:** put the exact text to find and the exact text to put in its

## Transcripts as HTML pages

Any project's transcripts become pages with one command:

    SCRIPTS/transcript-site/build-transcript-pages <project-dir>

It writes `llm-transcripts/HTML/`: one page per transcript, with the two
speakers on opposite sides, the recap list at the top ("How it went", each
entry linking into the conversation), every turn anchored (`#turn-N`) so an
issue or a documentation page can link to it, every commit line anchored
(`#commit-<seven>`), and links to helper transcripts pointing at their
pages; plus an `index.html`, the table of contents, built from the project's
commit history, each commit with a button that opens its conversation at the
line where it was made. The look is double-diaper-dungeon's.

The library is three parts that never load each other — `conversation/`,
`contents/` (the table of contents) and `films/` (a gif beside every
message, for a project that asks) — joined by `build-site.lua`. A project
changes anything (where its transcripts and history are, its colours,
films) with a `transcript-site.settings.lua`;
`SCRIPTS/transcript-site/README.md`
is the guide, and each file has an `.info.md`.

a project not in git (no history for the table of contents). Read every

## "Doesn't it just get received by Titan?"

You're right about mail coming **in**. When someone writes to
`develop@abcd-games.net`, it goes to Titan, and Titan keeps it in your mailbox.

Sending **out** works backwards, and that's the part with the wall. Here's the
trip a claim email takes:

1. The claim program runs on **your Linode**. It writes the email: "here's your
   link and your code."
2. To send it, the Linode **calls Titan's server**, `smtp.titan.email`, on
   **port 465**. It logs in as your mailbox and hands the email over. This call
   goes **out of the Linode**.
3. Titan signs it with your new DKIM key and carries it to the subscriber's
   inbox.

Step 2 is what Linode blocks. It won't let a new account's machine make
*outgoing* calls on ports 25, 465 or 587. So the email never reaches Titan in
the first place. The fix is the reverse-DNS-then-ask-support step.

There's also another road around the wall. Some mail-sending services (Postmark,
Resend and others) take emails over **port 443**, the ordinary web port, which
Linode never blocks. That's one more account, but no support ticket.

## "Shouldn't it be no-reply?"

That's a really good question. Your new DKIM signature covers **any** address at
`abcd-games.net` that Titan sends, so either choice is trusted the same. The
difference is what happens when someone presses **Reply**:

- **A no-reply address** (`no-reply@abcd-games.net`). Replies go nowhere, so
  your mailbox stays quiet. But a subscriber whose code doesn't work has no easy
  way to ask for help, and some spam filters trust no-reply senders a bit less.
  With Titan, it would need a second mailbox or an alias for that name.
- **A reply-able address** (`develop@`, or a new one like `hello@`). A
  subscriber who's stuck can just answer the email, and their message lands in
  your Titan mailbox.

For a claim email, the moment someone *paid* and something might go wrong, I
lean towards **reply-able**. What do you think? Do you want subscribers to be
able to write back to you, or would you rather they reach you some other way?
